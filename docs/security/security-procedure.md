# נוהל אבטחת מידע — Eccentric · Optimal Motion

לפי תקנה 4 לתקנות הגנת הפרטיות (אבטחת מידע), התשע"ז-2017. משלים את [מסמך הגדרות המאגר](database-definition.md).
**עדכון אחרון:** 16 באוקטובר 2026 · **סקירה:** פעם בשנה, ובכל שינוי מהותי.

> ⚠️ מסמך פנימי. אין לפרסם. מקומות המסומנים `[...]` דורשים השלמה. ✅ = קיים, ☐ = לביצוע.

## 1. רמת האבטחה
המאגר מכיל מידע בריאותי, ולכן הוא חייב לפחות ברמת אבטחה "בינונית". ייתכן שבמאגר עם עד 10 בעלי הרשאה חלה רמה מקלה יותר, אבל הנוהל נכתב לרמה הבינונית כדי לכסות את שתי האפשרויות. ☐ לאשר עם עו"ד.

## 2. ניהול גישה וחשבונות
החשבונות שנותנים גישה לכלל המידע:

| חשבון | מה הוא פותח | אימות דו-שלבי (2FA) |
|---|---|---|
| חשבון המנהל באפליקציה | כל המטופלים דרך קונסולת הניהול | ☐ (סיסמה חזקה + Passkey) |
| Supabase | המאגר כולו, כולל מפתח השירות | ☐ |
| Vercel | השרת ומשתני הסביבה (כל המפתחות) | ☐ |
| GitHub | הקוד ופריסה אוטומטית ל-Vercel | ☐ |
| Anthropic Console | מפתח ה-API | ☐ |
| חשבון Google / האימייל של העסק | שחזור סיסמה לכל השאר | ☐ |

כללים:
- כל חשבון שייך לאדם אחד. לא משתפים סיסמאות.
- הרשאת מנהל (`role = 'admin'`) ניתנת רק באמצעות SQL ישיר במאגר. אי אפשר לקבל אותה מתוך האפליקציה (נאכף ב-RLS ובטריגר `protect_patient_privileged_fields`).
- כשבעל הרשאה עוזב: מבטלים את הרשאת המנהל ואת הגישה לכל החשבונות בטבלה, ומחליפים מפתחות שהיו חשופים לו, באותו יום.
- סקירת בעלי ההרשאה פעם ברבעון: `select full_name, email from patients where role = 'admin';`

## 3. מפתחות וסודות
- ✅ מפתח השירות של Supabase, מפתח Anthropic ומפתח ה-VAPID הפרטי נמצאים רק במשתני סביבה בשרת (Vercel), ולא בקוד או ב-git (`.env.local` מוחרג ב-git).
- ✅ בדפדפן נמצאים רק המפתח הציבורי (anon) של Supabase ומפתח ה-VAPID הציבורי. זה בסדר, כי RLS הוא שמגן על המידע.
- מפתח שנחשף או שיש חשש שנחשף מוחלף מיד (ראו סעיף 7).

## 4. הגנה על המידע במערכת
- ✅ RLS בכל טבלה עם מידע אישי.
- ✅ כל פעולת שרת שעולה כסף או נוגעת במידע בודקת את זהות המשתמש (`verifyCaller`).
- ✅ כותרות אבטחה בשרת (`next.config.ts`): חסימת הטמעה במסגרת (clickjacking), HSTS ו-nosniff.
- ✅ אתגר ההתחברות עם Passkey נשמר בשרת לשימוש חד-פעמי, כדי שאי אפשר יהיה לשחזר התחברות.
- ☐ להפעיל "Leaked password protection" ב-Supabase (Auth → Settings), שחוסם סיסמאות שדלפו.
- ☐ לפני כל השקה ואחרי כל מיגרציה: להריץ את Security Advisor של Supabase, לעבור על מדיניות ה-RLS, ולרשום ב-[MISTAKES.md](../../MISTAKES.md) כל ממצא.

## 5. גיבויים
- ☐ לוודא את תוכנית הגיבוי של Supabase: [Free = אין גיבוי אוטומטי שאפשר לשחזר ממנו בעצמנו; Pro = גיבוי יומי ל-7 ימים]. כשיהיו משתמשים אמיתיים, נדרשת תוכנית עם גיבוי.
- ☐ לבדוק שחזור מגיבוי פעם בשנה.

## 6. תיעוד ובקרה
- Supabase שומר לוג של התחברויות ושל קריאות API (Logs Explorer). Vercel שומר לוג של בקשות לשרת.
- ☐ לבדוק את משך שמירת הלוגים בתוכנית הנוכחית. ברמה בינונית נדרש תיעוד גישה ל-24 חודשים לפחות. אם התוכנית שומרת פחות, צריך לייצא את הלוגים או לשדרג.
- ☐ לעבור על לוג ההתחברויות של חשבונות המנהל פעם בחודש.

## 7. אירוע אבטחה
**אירוע אבטחה** = כל חשד לגישה לא מורשית למידע, דליפת מפתח או סיסמה, מחיקה או שינוי של מידע שלא כמתוכנן, או ממצא אבטחה שאפשר היה לנצל.

**מה עושים, לפי הסדר:**
1. **עוצרים את הנזק.** מחליפים מיד מפתח שנחשף: service role ב-Supabase (Settings → API), מפתח Anthropic ומפתחות VAPID. אחר כך מעדכנים ב-Vercel ומבצעים redeploy. מנתקים את כל ההפעלות (sessions) של חשבון שנפרץ ומחליפים לו סיסמה. סוגרים את פרצת ה-RLS במיגרציה.
2. **מבררים מה קרה.** איזה מידע, של כמה משתמשים, ממתי ועד מתי. בודקים בלוגים של Supabase ו-Vercel.
3. **מתעדים** ביומן האירועים שלמטה: תאריך, מה קרה, מה נחשף, מה נעשה.
4. **מדווחים.** אם מדובר ב**אירוע אבטחה חמור**, כלומר שימוש, חשיפה או שינוי לא מורשים של מידע מהותי, ובמאגר הזה כל מידע בריאותי נחשב כזה, מדווחים **מיד** לרשות להגנת הפרטיות ופועלים לפי הנחיותיה, כולל הודעה למשתמשים שנפגעו אם תידרש. ☐ לאשר את נוסח החובה העדכני (אחרי תיקון 13) עם עו"ד.
5. **מסיקים לקחים.** מוסיפים רשומה ל-MISTAKES.md ומעדכנים את הנוהל.
